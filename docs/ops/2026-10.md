### 2026-10-12 21:45 — TASK-022 — DeepSeek (root cause of the `/media/` re-download found; fix implemented, NOT deployed)

**Why**: the 21:10 monitoring round established that `/media/` audio is re-downloaded in full, but the log format
(`combined`) does not record `If-None-Match`, so "does the client even try to revalidate?" was unanswerable from the
logs. Instead of adding a log format and a reload, the question was settled by replaying the client's own probe.

**How the client actually validates** (`android/src/fun/leio/stronghold/BundledAssets.java:170-196`, the Windows twin
is the same rule): one `HEAD` per path with `If-None-Match: <the ETag recorded at bundle time>`,
`Accept-Encoding: identity`, `Cache-Control: no-cache`; a file may be served from the bundled payload only when the
answer is `304`, or `200` with a byte-identical `ETag`. `canonicalPath()` maps `/media/<x>` → `/assets/audio/<x>.mp3`,
and the game requests audio through `/media/…` (the extension-less alias that exists to keep download managers from
hijacking `.mp3` URLs).

(`ngx_http_set_etag`), which is exactly the shape the bundle index stores. `/media/…` is **proxied to Node** →
`server/http/files.js:199` built `<size>-<mtime-ms>`. Same bytes, two different validators, so the client's
`If-None-Match` could never match on the route it uses for audio.
