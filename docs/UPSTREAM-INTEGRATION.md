# 上游版本并入流程

本项目不自动抓取、合并或部署上游提交。上游发布新版本时，由维护者按下面的步骤手动增量并入；不要直接用上游目录覆盖本项目。

1. **先固定当前版本。** 确认本仓库代码与线上版本、资源清单和客户端版本的对应关系；把当前工作推送到自己的仓库，并保存可回滚的服务端和客户端发布包。
2. **比较上游。** 分开审查规则/数据、网络协议、干员调配、资源、结算、大厅和游戏内 UI。记录每项是直接采用、适配还是暂不采用，以及理由。纸鸢 fork 的干员调配网格作为本项目的界面基线，官方 0.2.2 的潜能、练度、模组和语音数据在此基础上适配。
3. **保护自定义界面。** 游戏内顶部、盟约、卡牌、角色状态条、观战、房间入口与战绩卡片属于本项目的定制区域。只并入必要的上游逻辑或素材，不以解决代码冲突为理由恢复上游整套 UI；有意调整时须对照截图验证。
4. **分层验证。** 先跑改动对应的单元测试，再跑 `npm run typecheck`、`npm run lint`、`npm run ci` 和浏览器测试。玩法变更核对 golden，资源用 `npm run assets:merge` 重建并校验，不能手改 `data/*.json`。确认简中与其他语言包、网页与客户端两条资源路径都能工作。
5. **分阶段发布。** 先在独立测试地址验证版本和多人对局，待合作局结束再部署正式服；发布后检查健康状态、房间/观战、素材加载和客户端更新器。出错时回滚到第 1 步保存的版本，不能留下新旧协议混用的客户端。

上游以后有补丁时重复这套流程，**不恢复定时自动合并**。小型网页 UI 修复可单独部署；客户端程序变更仍需按更新器的版本及差分包机制发布，不能假设网页发布会更新已安装的客户端。
